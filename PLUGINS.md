# Плагины — стандарт

Writer делится на ядро и плагины, как VS Code на редактор и расширения. Ядро — книга и её блоки, дерево, два редактора, заголовки разделов. Остальное постепенно уходит в плагины: оформление, ссылки и источники, публикация, проверка орфографии, импорт и экспорт Word.

Принципы:

- плагин зависит только от ядра и не импортирует ни ядро, ни другие плагины. Ядро зовёт его хуки и передаёт всё, что нужно, аргументами;
- всё, что плагин добавляет, видно из его папки: манифест и хуки. Ядро ничего не знает о плагине заранее;
- плагин ставится папкой: положить её в папку плагинов или импортировать `.zip` в панели «Расширения»;
- Python-зависимости живут в образе api. Плагин, которому не хватает библиотеки, панель показывает с ошибкой импорта. Ставить зависимости на лету пока не умеем.

Сейчас по стандарту работают два плагина: «Научная статья» (`plugins/article-style`) и «Оформление по образцу» (`plugins/sample-style`).

## Папка плагина

```
plugins/                             PLUGINS_DIR в .env, общая для всех книг
├── .корзина/                        удалённые и заменённые новой версией плагины
└── article-style/                   имя папки — id плагина: латиница, цифры, «-»
    ├── plugin.json                  манифест
    ├── api.py                       хуки ядра; необязателен
    ├── build.py                     свои модули: api.py берёт их «from . import build»
    └── templates/                   свои файлы плагина
```

Включён ли плагин и как настроен — в каждой книге свой выбор, файл `плагины.json` в её корне:

```json
{"article-style": {"enabled": true, "values": {"preset": "article"}}}
```

Плагина в файле нет — он включён, настройки у него по умолчанию. Файлы из настроек плагина лежат в книге, в скрытой папке `.плагины/<id плагина>/`. Там же плагин может хранить своё для этой книги — например, разобранный образец: скрытыми файлами, чтобы не спутать их с файлами настроек.

## Манифест plugin.json

```json
{
  "name": "Научная статья",
  "version": "0.1.0",
  "description": "Что делает плагин: панель показывает это в карточке",
  "settings": {
    "preset": {
      "title": "Требования к оформлению",
      "choices": {"article": "Научная статья", "apa-7": "APA, 7-е издание"},
      "default": "article"
    }
  }
}
```

`settings` — настройки плагина в книге. Поля рисует сама панель «Расширения», плагину своя вёрстка не нужна. Видов два:

- выбор из списка — `title`, `choices`, `default`, как выше;
- файл — `{"kind": "file", "title": "Образец оформления", "accept": [".pdf", ".docx"]}`. Панель даёт загрузить, заменить и убрать его. Загрузка — `PUT /api/plugins/<id>/files/<ключ>?name=<имя файла>`, тело — сам файл. Ядро кладёт файл в папку плагина в книге и сразу зовёт хук `template`. Плагин разбирает файл, а ядро ставит в office шрифты, которых там нет, из получившегося шаблона. Упал хук или шрифта нет нигде — файл не принимается, остаётся прежний. Хук получает путь файла, пусто — файла нет.

### Язык интерфейса

Строки манифеста пишут по-русски, а переводы кладут рядом, в `translations`: язык → строка → перевод. Ядро само показывает название, описание, подписи настроек и пункты выбора на языке интерфейса, строку без перевода — как есть:

```json
"translations": {"en": {"Научная статья": "Scientific article", "APA, 7-е издание": "APA, 7th edition"}}
```

Свои тексты — то, что отдаёт `describe`, и ошибки хуков — плагин переводит сам. Язык интерфейса — `config.app.language` из `app.settings.config` (`ru` или `en`): плагин работает внутри api. Так сделано в «Оформлении по образцу», см. его `words.py`.

## Хуки — api.py

Модуль с функциями, имена которых знает ядро. Ядро выполняет `api.py` заново при каждом вызове хука, вместе с другими модулями плагина. Поэтому импортированный плагин работает сразу, без перезапуска api, а состояния между вызовами у плагина нет. Папка плагина — пакет Python: `api.py` берёт свои модули рядом относительным импортом, `from . import pdf`. Хук получает настройки плагина в книге — словарь `values`.

| Хук | Когда | Что возвращает |
|---|---|---|
| `template(values)` | новый текст блока, сборка публикации, загрузка файла настройки | путь к шаблону `.docx` или None |
| `describe(values)` | панель «Расширения» показывает плагин | что плагин сообщает о себе в этой книге, строками, или None |

Ядро зовёт хук у включённых плагинов по имени папки, побеждает первый ответ не None. Нет такого ответа — шаблон из корня книги, иначе пустой документ. Упавший хук останавливает действие ошибкой «Ошибка плагина: id: …»: оформление молча не подменяется. Если после загрузки файла настройки шаблон книги даёт другой плагин, панель говорит, какой: его стоит выключить в книге.

Шрифты шаблона ядро ставит в office само: каких в office нет, оно скачивает из Google Fonts в папку шрифтов (`FONTS_DIR`), а имена шрифтов в шаблоне приводит к тем, под которыми их знает office. Поэтому плагин пишет в шаблон шрифт, как его назвал образец: «PT Serif» или «PTSerif».

Шаблон решает и то, что раньше ядро задавало по ГОСТ 7.32: номер списка 0 в стиле «Heading 1» (`<w:numPr><w:numId w:val="0"/></w:numPr>`) — заголовки без номеров, как в APA. Иначе ядро нумерует их «1», «1.1», «1.1.1». Страницы публикации шаблон не решает: каждый блок, содержание и список источников — с новой страницы, таблица не рвётся, при любом шаблоне.

Правило ядра действует и для плагинов: текст, который office может держать открытым, на диске не менять.

## Импорт .zip

В архиве одна папка, названная id плагина, в ней `plugin.json`. Api принимает архив до 20 МБ (и сжатый, и распакованный), только с типом `application/zip`: такой запрос браузер не отправит с чужого сайта без разрешения CORS. Плагин — код, который выполняет api с доступом к книге и библиотеке на чтение, поэтому ставить стоит только плагины, которым доверяешь. Каталога плагинов из интернета нет.

## Что дальше

Следующие плагины потребуют расширить стандарт. Добавлять это по мере надобности, не раньше:

- `router` в `api.py` — свои ручки плагина под `/api/plugins/<id>`. Нужен проверке орфографии;
- `web.js` — модуль оболочки с `activate(core)`: кнопки у блока, свои области панели, окна, шина сообщений с плагином редактора. Нужен ссылкам и публикации;
- `office/` — свой плагин ONLYOFFICE. Office отдаёт плагины из `sdkjs-plugins`, туда смонтирована одна папка `app/plugin`. Придётся смонтировать папку плагинов целиком, а это пересоздание office;
- `requires` в манифесте — зависимость от другого плагина. Например, ссылки дописывают список литературы в публикацию;
- новые хуки: `publication_end` — дописать в конец публикации, `block_created`, `block_removed`;
- «Научная статья» и «Оформление по образцу»: применить оформление к уже написанным текстам. Закрытые тексты может перевести api, открытый — только плагин редактора.

Порядок перехода: проверка орфографии (ни с чем не связана) → публикация → ссылки и источники → импорт и экспорт Word.

Экспорт и импорт своего формата пока сделаны в ядре (`service/book/transfer.py`, 2026-11-09), см. CLAUDE.md «Экспорт и импорт»: публикация несёт всю папку книги в скрытой части customXml, импорт её распаковывает, файл без неё — ошибка. Импорт чужого документа Word — потом, отдельным плагином. Он режет документ на блоки по заголовкам первого уровня. Каждый блок — копия документа без чужих кусков, поэтому сноски, формулы и стили остаются. Разрезку проверили на копии публикации 2026-11-06. Вид блока плагин узнаёт по названию структурного элемента ГОСТ 7.32, заголовки в своих стилях приводит к «Heading 1–4», номера, набранные руками, снимает.
